2026-07-19 · packages/db (wt-db) — `public.resolve_brand_memory` shipped (SECURITY DEFINER Brand Brain write RPC answering wt-web's blocker: role-allowlisted members, per-workspace advisory lock, supersede-then-insert versioning, content-based replay, optional CAS via `p_expected_version`). Decisions: (1) idempotency is content-based (jsonb equality against the active row) so it needs NO new column — but the CAS check runs BEFORE the replay branch, so an identical resubmit carrying a stale expected_version conflicts rather than replays; documented in the `@sahoda/shared` doc comment because that is wt-web's only reference, not the migration. (2) `system` → `resolved|manual` on identical content DOES mint a version — provenance is the change; the reverse direction replays, so a fallback can never relabel a genuine brain. (3) `max(version)` must span ALL statuses: `unique (workspace_id, version)` is unconditional and the CHECK admits `draft`, so an active-only max collides. (4) Guards must run BEFORE the advisory lock or any authenticated stranger makes the server take an arbitrary workspace's lock; the `v_ws_id` data dependency enforces that structurally (reordering yields a null lock key), and nothing after the membership select reads `p_workspace_id` again — cross-tenant writes are impossible by construction, not by check. (5) The SQL shape guard pins arrays + signal_lock only, NOT scalars or element types: zod stays the authority, and re-implementing BrandMemoryPayloadSchema in SQL would break single-source-of-truth. (6) Payload capped at 32 KB / 40 list entries because brand_memory feeds the mesh brand-context prefix prepended to EVERY model call — an oversized brain bills provider tokens forever against a fixed credit price. Gotchas: (a) Postgres guards are not NULL-total by default — `jsonb_typeof(null) <> 'object'` is NULL, not true, so an explicit JSON null (PostgREST forwards it verbatim; only an OMITTED arg takes the default) walks past a naive check into a raw 23502; use `is distinct from` / `coalesce`. (b) Mutation-tested all 28 live tests: 11 injected regressions, 11 caught — but three separate null-permeability mutations stayed GREEN because the guard is null-total in three independent places, so "test still passes" needed the whole validation block neutered to prove teeth. (c) Known redundancy shipped: `brand_memory_workspace_version_idx` is already covered by the frozen `unique (workspace_id, version)` btree — a later migration should drop it AND the frozen `(workspace_id)` index; not fixed in place because editing an applied migration is forbidden. (d) Adding a 5th live test file pushed `packages/db` past vitest's 5s default `testTimeout` and surfaced as 4 timeouts — two of them in the untouched `bootstrap.test.ts`. These suites hit the real Supabase over the network with files running in parallel, so the default was always wrong; added `packages/db/vitest.config.ts` (30s test+hook timeout). A live-DB timeout looks exactly like a logic failure — check the clock before the SQL.
