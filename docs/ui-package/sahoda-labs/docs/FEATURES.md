# Feature catalogue

Every feature, what it does, and **why it is built that way**. The rationale is
the part worth keeping — the code can be rewritten, the reasoning is what makes
the rewrite come out right.

Ordered by how much each contributes to the product feeling finished.

---

## 1. Rapid review (Approvals)

**What.** Approvals is a queue, not a list. Decide → the row animates out → the
counter reads `Reviewed 3 of 5` → the next item takes focus. `A` approve, `R`
reject, `E` edit, `J`/`K` move, `Enter` open, `?` help.

**Why.** This is the highest-frequency screen in the product. A user reviewing
twelve items should not touch the mouse twelve times, and should never lose their
place. The counter exists because "how much is left" is the question you actually
have while working through a queue — a bare list cannot answer it.

**Implementation notes.**
- Decisions are optimistic. The row exits, counts tick, the sidebar badge
  updates — no refetch. `Approvals.syncAfterDecision()` repaints only what
  changed, so scroll position and the exit animation survive.
- The session counter (`Approvals.session`) starts at the **first decision**, not
  at page load, so it measures this sitting rather than all time.
- Bulk actions stagger by 70ms so a multi-approve reads as several things
  happening, not one flicker.
- Shortcuts stand down while typing **and** while any overlay is open.

**Do not lose:** the optimistic exit. Re-fetching the list after each approval
turns a 300ms interaction into a 900ms one and destroys the sense of speed.

## 2. The mascot as a status surface

**What.** The chat launcher is the robot's head, showing one of four
expressions. Red = something is broken. Amber = a high-priority approval waits.
Blue = AI is working. Green = all clear.

**Why.** It reports the workspace **before you open it**. A red face in the
corner is a faster signal than a number in a badge, and it is glanceable from
across a desk.

**The property that makes it honest:** every surface reads one function,
`workspaceMood()`, which derives the face from the same collections the pages
render. The mascot structurally cannot contradict the UI. Keep that when you port
it — the moment the face comes from a separate field, it will drift.

---

## 3. Guided flows with real failure

**What.** Connecting an integration is a step sequence — opening secure window →
authenticating → granting permissions → syncing. Search Console **deliberately
fails** on first attempt, and the failure explains what happened, confirms
nothing changed, and offers Verify-and-retry / different account / support.

**Why.** Error recovery that is never exercised is never designed. Building one
honest failure into the demo forced the recovery path to be real. Most products
have a beautiful happy path and a bare `Error.` toast.

**Rule:** every error names a cause, states what is unchanged, and offers the
button that fixes it.

## 4. AI that reports work

**What.** `AITask` shows one live step and completed ones ticked. Generated text
streams in. Every generation ends with *Generated by Sahoda AI* + Copy / Edit /
Regenerate / Accept.

**Why.** A spinner says "wait". A step list says "I am reading your documents,
then comparing competitors". The second builds trust in the output; the first
builds impatience. The completion is signalled by the mascot changing expression
— the state change *is* the message.

**Streaming matters more than it looks.** Text arriving progressively reads as
being written. The same text pasted in one frame reads as a page load. Same
duration, different perceived intelligence.

**Anti-pattern this avoids:** turning every screen into a chatbot. AI is embedded
in workflows — reasoning inside an approval row, a health gate before campaign
launch, a suggested reply in the inbox. The chat exists for open questions, not
as the primary interface.

## 5. One conversational AI surface

**What.** The header sparkle, per-page contextual buttons, the command palette
and Home's ask bar **all open the same chat panel**. `App.askAI()` delegates to
`Chat`.

**Why.** Two places to talk to one assistant is duplication users have to learn
around. During the build this started as a drawer *and* a chat; consolidating
deleted ~4,800 characters and made the product simpler to explain.

**Replies are grounded.** `Chat.answer()` is a lookup over `DB` — ask what to
approve first and it names the actual top item, its real priority, its real due
time and its real AI reasoning. When you connect a model, pass that same context
in, so the assistant still cannot contradict the page behind it.

---

## 6. Command palette

**What.** `⌘K`. Opens on **Recent + Suggested**, not a blank list. Match
highlighting, prefix matches sorted first, grouped by type, arrow-key navigable,
real no-results state.

**Why.** An empty palette teaches users it is not worth opening. Suggestions are
derived from actual state — "Review 5 pending approvals", "Fix a broken
connection" — so the first thing you see is the thing you probably came for.

---

## 7. Optimistic updates with undo

**What.** Approving from Home ticks the count, drops the card, prepends an
activity line and updates the sidebar badge with no reload. The toast offers
**Undo**.

**Why.** Undo is faster and less annoying than a confirmation dialog for
reversible actions. Confirm dialogs should be reserved for the genuinely
destructive.

---

## 8. Context-preserving navigation

**What.** Detail always opens in a **drawer**, never a page navigation. Back
links **name where they return to**, from an actual navigation trail. Every
object has a deep link.

**Why.** The list behind a drawer is the context. Navigating away destroys the
scroll position, the filter and the place in the queue. And a back button
labelled "Back" is a guess; one labelled "Whitening Launch" is information.

---

## 9. Motion with a job

Every animation answers one question: what changed, where did it come from, where
did it go, what is happening, what needs me, what worked.

| Movement | Duration | Says |
|---|---|---|
| Page content enters | 280ms | You navigated; the shell did not |
| List rows stagger | 200ms / 22ms apart | These arrived together |
| Button press | 90ms `scale(.98)` | Received |
| Card hover | 200ms, 1px lift | Clickable |
| Row leaves | 220ms slide right | Decided and gone |
| Drawer slides | 280ms | It came from the edge |
| Modal scales 0.98→1 | 200ms | Focus moved here |
| Chart line draws | 700ms, once | Follow the trend |
| Mascot breathes | 1.6s loop, only while working | Something is happening |

**Only `transform` and `opacity`** — both composite on the GPU, neither triggers
layout.

**The scrim is 28% black with no blur.** A drawer belongs to the page behind it;
blurring that page denies the relationship and makes the drawer feel like a
different screen.

## 10. Status without colour

Four rungs: solid orange (shouts) → solid black (current) → orange outline
(pending) → grey outline (resolved). Meaning comes from fill weight, a glyph and
a label.

**Why.** The brand is five colours with no green/red pair available. Rather than
smuggling extra hues in, status is encoded in weight and iconography — which also
happens to survive colour-blindness and greyscale printing.

---

## 11. Autosave and unsaved-changes guard

Create flows autosave on every meaningful change (`Saving… → Saved just now`)
and intercept close with a three-way dialog: Discard / Keep editing / Save.

**Why.** Losing a half-written post to a stray click is the kind of thing users
do not forgive. The indicator is deliberately quiet — it reassures without
demanding attention.

---

## 12. Conflict as a decision

Dragging a planner post onto a slot that already has one on the same channel at
the same hour opens a dialog: pick another time, or schedule anyway.

**Why.** Silent overwrite is data loss. Silent rejection is confusing. Naming the
conflict and offering both options treats the user as the one who decides.

**Server note:** return `409` with the conflicting event so the client can show
this without re-deriving it.

---

## 13. Mobile recomposed, not shrunk

- Own header, bottom navigation with a dominant `+`
- Drawers become bottom sheets with a drag handle and swipe-to-close
- Approval rows become a grid — full title, meta on its own line, full-width
  actions — instead of truncating to "Insta…"
- Metrics become a snap-scrolling strip
- Every tappable control clears 44px; desktop stays dense

**Why.** Density is right on a desktop and wrong under a thumb. A responsive
layout that only reflows columns produces a screen that technically fits and
practically does not.

---

## 14. Every state designed

| State | Treatment |
|---|---|
| Empty | What the area does · why it is empty · what to do next |
| Loading | Skeletons that mirror the real layout; AI reports steps |
| Error | Cause · what is unchanged · the button that fixes it |
| Success | Toast for small things, a confirmation step for flows |
| No results | Names the query, suggests a shorter term |
| Disabled | Visually distinct and not focus-trapping |

---

## 15. Accessibility

- Focus trapped inside dialogs, restored to the opener on close
- `aria-current="page"` on active navigation
- Landmarks: `<nav aria-label>`, `<main>`, `role="dialog"` + `aria-modal`
- Live regions on the review counter, chat log and toasts
- Keyboard-visible focus everywhere; dialog containers focus **silently**
  (they take focus for screen readers but must not draw a ring)
- `prefers-reduced-motion` removes decorative loops, keeps state transitions
- Status never conveyed by colour alone

## If you can only port five things

1. **The four-rung status ladder** — it is the whole visual language.
2. **`runAction`** — the button lifecycle appears on every screen.
3. **Optimistic mutation with undo** — this is what "fast" actually means.
4. **`AITask` + streaming** — this is what "intelligent" actually means.
5. **The page-entry transition** — 280ms that makes navigation feel continuous.
