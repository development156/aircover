# 50 · Scope — the corrections layer

**25 August 2026, research lane, at `e4e2021`.** Scoped, not built. It needs a
migration this lane cannot write and an owner ruling on retention.

The founder's ruling, 25 August: **store corrections, not conclusions.**

---

## The argument, in one paragraph

The visible Brand Brain holds conclusions: voice, persona, hook, red lines. A
hidden layer holding more conclusions is a second copy of the same thing, and it
is the part a competitor reproduces the moment the customer re-types their brand
description somewhere else. What cannot be reproduced is the record of **how
this business fixes what Sahoda wrote**, because that only exists if Sahoda
wrote the draft. It is generated by using the product rather than by the
business succeeding, so it accumulates from day one with no threshold to clear,
and no export hands it to anybody.

---

## The finding that changes the size of this

**Two of the three streams need no migration.** The data is already on disk,
append-only, and derivable retroactively for every workspace that has ever used
the product. Only stream 1 needs a schema change, and it is the one recorded as
`apps/web/REQUESTS.md` §22 because it is losing history every day.

| stream                 | the correction it records                         | on disk today?               |
| ---------------------- | -------------------------------------------------- | ----------------------------- |
| 1 · rewrite deltas     | what they changed about a caption Sahoda wrote      | **no** — the edit overwrites  |
| 2 · brain corrections  | which resolved guesses they rewrote, and to what    | **yes** — derivable now       |
| 3 · rule overrides     | which gate findings they went ahead past            | **yes** — derivable now       |

---

## Stream 2 · Brain corrections — derivable today

`brand_memory` is append-only: `unique (workspace_id, version)`, one active row,
old versions kept as `superseded`. Inside the payload, `payload.field_meta`
stamps registered fields with `{ kind, confirmed, source }` where source is
`model` or `owner`, and `field-meta.ts` states the two rules that keep it honest
— a regenerate returning the same text leaves a confirmation standing, a
regenerate returning different text demotes the field to a guess.

**`field_meta` is optional and older rows have none**, which is stated in its own
header: every version written before it existed carries no stamp. That does not
block the read. Authorship for those is recovered the way it always was, by
diffing consecutive payloads — the stamp is a convenience on newer rows, not the
only route, and a correction record built only from diffs is complete for the
whole history.

So for any workspace, diffing consecutive versions over `BRAIN_FIELDS` gives
exactly the correction record: the path, the model's sentence, the person's
sentence, and the version each belongs to. `editedPaths` already computes the
path list for a single pair; it is a pure function over two payloads and nothing
stops it being run across the history.

**Nothing needs to be stored to begin.** What is missing is a reader, and the
decision about what the aggregate is FOR.

**The cross-customer half is the more valuable one, and the more dangerous.** If
eleven bakeries all rewrite the same resolved field, the resolver is wrong for
bakeries, and that is an asset no single-tenant view can see. It is also a read
across workspaces, which nothing in this product currently does, and it must
never put one customer's sentences in front of another. The safe shape is
counts and field paths, never text. **Owner ruling required before any
cross-workspace read is written.**

## Stream 3 · Rule overrides — derivable today, with one gap

`post_publish_logs` is append-only and its `error` jsonb carries the whole gate
verdict on a block or a hold: `decision`, `ruleSetVersion`, `brandVersion`, the
regime and its basis, and per finding the `ruleId`, `tier`, `statement`, the
`quote` from their post and the `rewrite` that was suggested.

Pairing a blocked row with a later succeeded row for the same post says whether
the person complied or went ahead. That is the override record, and it is
already written.

**The gap:** the log holds no body, so it says a rule was overridden and not
what the person changed to get past it. That half needs stream 1. Stream 3 is
worth reading on its own regardless — a rule overridden by most customers most
of the time is a rule that is wrong, and today nobody counts that.

## Stream 1 · Rewrite deltas — the one that needs the migration

`posts.body` and `post_variants.body` are single mutable columns and there is no
revision table in any migration. Every save overwrites what the model produced.
The storage ask is REQUESTS §22 and its two options are a `generated_body`
column beside `body`, or a `post_revisions` row per save; the db lane chooses.

The seams where a model's text becomes a post body, so the write has a place to
go rather than being retrofitted later:

- `apps/jobs/src/ai/postsStore.ts` — `plan_week` inserting posts
- `apps/web/src/app/actions/plan-week.ts`, `loop-create.ts`, `playbook-run.ts` —
  the same, from the web side
- `apps/web/src/app/actions/posts-ai.ts` — `caption_rewrite`, which returns text
  to the editor and never touches a row itself

That last one is the interesting case and it is an owner call: a rewrite produces
a before-and-after even when nothing is published, and it is the highest-signal
pair in the product, because the person asked for the change and then changed it
again.

### What a delta record holds

Not prose, and not a model's opinion of the change. Measurable properties only,
so the record cannot drift from what happened:

- characters and words, before and after, and the signed difference
- did the first sentence survive, verbatim or at all
- emoji count before and after (**never a judgement** — see §3 of the copy rules:
  emoji are native to social captions and stripping them is a regression)
- hashtags added and removed
- links added and removed
- whether a `@mention` was touched
- for a variant, whether the change moved it toward or away from the channel limit

Aggregated per workspace, that is a description of taste. Aggregated across
workspaces in the same trade, it is a description of the resolver's blind spots.

## What must be true before any of it reaches a prompt

This is the part that decides whether the feature is trustworthy, and it is
where the existing rules already point.

1. **Deltas are facts; the summary of them is not.** `reflect.ts` establishes the
   principle for the Loop and it holds here: a claim about the customer's own
   business is computed, never generated. "Your posts run 40% shorter than the
   drafts" is arithmetic. "You prefer a punchy, no-nonsense voice" is a
   conclusion, and conclusions belong in the visible Brain where a person can
   confirm or reject them.
2. **So the path into the Brain is a proposal, not a write.** `memory_events`
   exists, `propose_memory_event` writes into it, `/loop` shows what is pending
   and `resolve_memory_event` accepts one into a new version. `docs/49` found
   that whole machinery already built. A learned preference goes through it and
   is confirmed by a person, exactly like a Loop learning.
3. **`alignment.note` is not a home for this.** `docs/49` §3: it is in neither
   `BRAIN_FIELDS` nor `DERIVED_FIELDS`, so a value written there cannot be
   edited, confirmed or counted. Whatever the corrections layer proposes must
   land in a field the confirmation machinery can see, or the field list has to
   grow first.
4. **Stored drafts are customer content.** Retention belongs in the same
   conversation as the rest of the data policy, and it is an owner ruling, not a
   default.

---

## The measure that keeps it honest

**Average edit distance per post should fall over months, per workspace.**

If it does not, the learning is decorative, and no screen may say the Brain is
getting smarter. It is also the customer-facing version of the moat: outputs
needing less fixing is a thing a person feels, which a number in a dashboard is
not.

Computable the moment stream 1 has two months of rows, and worth putting on a
screen only once it has been watched privately for long enough to know it moves.

---

## Build order

1. **The db lane:** REQUESTS §22. Nothing in stream 1 exists until it lands, and
   every day it does not, more history is gone.
2. **A reader for stream 2**, over the version history that is already there. No
   migration, no new writes, and it produces a real number this week: how many
   resolved fields does a typical customer rewrite, and which ones.
3. **A reader for stream 3**, over `post_publish_logs`. Same shape, same day.
   Which rules get overridden, and how often.
4. **Then decide what a proposal looks like**, informed by 2 and 3 rather than
   by this file. The proposal path itself is built (`docs/49`).
5. **The delta computation**, once stream 1 has rows.

Steps 2 and 3 are the cheap ones and they are also the honest ones: they measure
what customers are already correcting, before anybody designs a schema around a
guess about it.

---

## What this scope cannot see

No production row. Not one `brand_memory` version diff, not one
`post_publish_logs` error payload, not one real correction. Every claim above is
read from source and from the migrations. Whether customers correct enough for
any of this to matter is exactly what steps 2 and 3 exist to find out, and it is
possible the answer is that they barely edit at all — in which case the moat is
somewhere else and this file was worth writing to learn that.
