Closed High

Radar had no guard whatsoever. scripts/radar-pass.ts handed globalThis.fetch to the nightly pass and cheap-check.ts asked it for redirect: 'follow', so every hop resolved inside undici where nothing of ours could see it. app.radar_normalize_locator stores 169.254.169.254 happily — its domain pattern is dotted [a-z0-9-] labels, which a dotted quad satisfies. 1 · The call that produces the Brand Brain fenced nothing

Closed Medium

The door's own call quarantines everything it reads. brand_guidelines — the second call, the one that actually decides the Brain — sent JSON.stringify(input) as its whole user turn, and two of that object's fields are sentences lifted verbatim from a page or PDF at an address the customer typed. No fence, no attribution, no preamble.

And the selection is attacker-controlled. Measured while writing the fix:

MeasuredfirstProofPoint() takes the first sentence carrying a number. <<<UNTRUSTED_PAGE index=0 url="forged" carries one. So the hostile page CHOSE which of its own lines we would quote — and chose a forged delimiter.

Fixed with quarantineInline, a new one-line shape sharing the same tokens and the same neutralizer as quarantineBlock — a second fence made of markers the neutralizer does not know about is a door nobody is watching. Applied where provenance is known, since the task cannot tell a founder's typed answer from a stranger's page. A cross-package parity test fails if the prompt and the fence ever name different markers.

2 · The gate's fence was forgeable, and its adversary is the post's author

Closed Medium

gate_classify fenced the post with <<<POST … POST and its comment claimed "the same quarantine shape brand_extract uses". It was not: those markers are unknown to neutralize, and the closer is the bare word POST alone on a line — reachable on purpose, and reachable by accident in a listicle. Every other quarantine here defends against a stranger's web page; this one defends against the customer, because the gate exists to stop them publishing something they may not.

The fix is a nonce, not a neutralizer, and the reason is three lines above it in the same file: the prompt requires quote to be the post's words copied character for character so the UI can find them in the stored post. Rewriting System: inside the text — which is what neutralising does — would make every quote of that span un-findable. ctx.traceId is already a fresh UUID per run, so the marker is per-call, deterministic for one call, and traceable.

3 · A filename could add a line to the prompt

Closed Medium

brand_extract interpolated Filename: ${filename} raw, one line beneath the four sentences saying the attached document is evidence. The upload door validates the data URL's type and size and nothing about the name, and a multipart part carries whatever the client wrote — so a newline in a filename adds a fifth sentence that the customer wrote. Business name had the same shape in both branches; both are fixed, because leaving one of a pair is how the sibling walks through.

JSON.stringify is enough here and the code says why it is not enough in general: it escapes newlines, which is the attack against a line-oriented framing, and it does not escape < or >, which is exactly what defeated the block header once before. A 200-character cap is the second half — a 50,000-character filename pushes our own instructions out of a 2,048-token budget.

Radar's strongest claim was a sentence in a header. It is now an assertion.

Session and auth

  • Token expiry mid-action. The Supabase client resolves accessToken per call from auth().getToken(); an expired session yields null, the client falls back to anon, and RLS denies. There is no cached token to outlive its session.
  • Can a revoked member still act? No cache exists to go stale. Every policy resolves through app.member_workspace_ids(), which reads workspace_members against auth.jwt() ->> 'sub' on every query, so removal takes effect on the next statement. The same holds for ops_admins: the middleware asks PostgREST through the caller's own token, so a revoked seat is refused by RLS rather than by a cached boolean.
  • Signing out. There is no server-side session state to kill — apps/web has no service-role client and holds nothing per-user between requests. Clearing the Clerk cookie is the whole of it, and the middleware's catch branch deliberately clears a corrupted __session rather than looping a redirect that would carry it straight back.

And one nobody was looking for

95% of the audit log is one row that names nothing

Fixed, unapplied Medium

Found while reconciling the row counts this audit was required to leave clean.

Measured in productionops_audit_log 12,839 rows action='user.created', actor='clerk:webhook' 12,196 rows (95%) distinct target_id among them 1 — the empty string newest meta {"linked_application": false, "linked_admin_seat": false} first 2026-07-28, last one four minutes before the fix

ops_application_link_user runs on every Clerk user.created. It tries to mark a beta application joined, tries to link a seeded admin seat, then writes an audit row unconditionally. coalesce(app_id::text, '') is the tell: the row records that it has nothing to record. Almost every sign-up matches neither, and the E2E suite mints Clerk users against this production instance on every gate run — 1,054 in one hour on 2026-08-22.

The first reading of this was wrong, and that is worth recording. Twelve thousand user.created rows read as twelve thousand production accounts. They are one user id logged twelve thousand times. Counting distinct target_id before raising it is the difference between an account-sprawl incident and an idempotency defect.

It is a security defect and not housekeeping: an audit trail that is 95% content-free is one nobody reads, and what is buried is admin.role, admin.revoke, admin.upsert and credit.*. That is the ordinary shape of anti-forensics — you do not delete the entry, you make the log unusable — and anyone who could trigger sign-ups could bury their own admin.role row.

The other direction mattered as much: this row is the only record that a Clerk account was bound to an admin seat. Every test comes in a pair, and the spec mutates both ways — including "nothing is ever written", which a careless fix would have passed.

The 12,196 existing rows are not deleted, and that is not caution — the table refuses it. delete from ops_audit_log raises "append-only: DELETE on ops_audit_log is not permitted", which the test discovered by trying. The predicate an owner would need is written into the migration.

P5The harness lied four times

The last audit found three defects in its own tooling. This one found four more, and every one of them manufactured a passing verdict. They are listed first among the fixes because nothing else in this report could be trusted until they were closed.

1 · A per-mutant cwd was silently ignored

Fixed

spec.cwd was read once and closed over, so a spec whose mutants each named a directory ran every command from the repo root. pnpm vitest run src/ip.test.ts finds no test files there and exits 1 — and exit 1 is what the runner calls KILLED.

The first run of the SSRF specmutation-check: 11/11 mutants killed … every row read "no test summary found in the output" Assertions actually executed: ZERO.

The tell was in the report the whole time. It is now a refusal, not a footnote.

2 · A zero-assertion run counted as a kill

Fixed

Tests 6 skipped (6). The mutated SQL made beforeAll throw, every test was skipped, the process exited non-zero, and that was scored as a kill. It is also exactly what a worker crash looks like when three sessions share a machine and PGlite is the memory-hungry one — the skip count is the tell, and it is now read rather than displayed. A run must show at least one test that passed or failed before its exit code means anything. One mutant legitimately breaks a fixture and must run no tests; it now declares that (expectsNoTests) where a reviewer can see it.

3 · Every PL/pgSQL mutant corrupted its own dollar quote

Fixed

String.prototype.replace treats $ in a replacement string as an escape. A PL/pgSQL body is delimited by $$, so any SQL mutant carrying one wrote $; where it meant $$; — unbalancing the quote and making every function below it a syntax error.

Measuredthe same mutant, applied by hand: 4 failed | 3 passed ← a real kill the same mutant, via the harness: Tests 7 skipped (7) ← scored as a kill 'a'.replace('a', '$$;') → '$;' 'a'.replace('a', '$1') → '$1' ← safe, checked, not assumed

Two shipped specs were affected — rls-enforced.mjs and jobs-integration-executes.mjs, which between them are the repository's proof that tenant isolation and the ledger function bite. Both re-run honestly: 9/9 and 3/3, now for the stated reason. A replacer function is substituted verbatim, and the harness now also asserts the replacement text is present after the write.

4 · SIGKILL leaves a mutant applied

Recorded

A mutant that made a stream unbounded had to be killed mid-run, and the harness's restore cannot survive SIGKILL — it left guarded-fetch.ts carrying its mutation. Recovered from the harness's own verified backup after diffing every other backup against its source to prove nothing else was stranded. Worth knowing rather than fixing: the backup was there and was hash-verified, which is what made recovery a diff rather than an investigation.

5 · A stranded mutant reads as a broken spec

Fixed

The consequence of 4, and it cost two diagnoses before it was worth fixing. An interrupted run leaves its last mutant applied; the next run then reports "expected exactly 1 occurrence, found 0", which reads as a broken SPEC and sends you to edit a spec that is perfectly correct. The signal is exact — the target is gone and the text it would have been replaced BY is present — so the harness now says so, and prints the git checkout that fixes it.

Both interruptions were self-inflicted: once killing a mutant that made a stream unbounded, once a two-minute command timeout cutting a run off mid-mutation.

Three survivors, and one wrong claim of my own

A survivor is only worth something if it means something, so all three were chased to the end. One was a real gap — counting could_not_check did not distinguish "we refused to look" from "we looked and it did not answer", and the assertion now reads transport: UnsafeUrlError, which can only be produced before a socket exists. The other was an equivalence, removed with the check that proved it. The third was an equivalent mutant of my OWN making — a "make the fence constant" edit that left ${ctx.traceId} in place, so the marker still varied and the mutant could not fail. A wasted survivor is worse than none: it trains the reader to skim past the next one.

Two of this file's find strings also went stale when prettier reformatted the sources under them, and the harness REFUSED both rather than scoring them — which is the guard working, and also a real way a mutation spec can quietly stop covering the thing it names.

And a comment I wrote myself claimed a signed bitmask makes 224.0.0.0/4 "silently stop matching". Measured: 0 divergences over 3,000,075 comparisons. Both sides go through the same ToInt32, so the sign cancels. The claim is corrected in the file rather than quietly dropped.

HonestyWhat I could not prove

  • Whether Vercel appends to or overwrites x-forwarded-for. The fix is correct under both, which is why it was made without waiting to find out — but the severity of the original defect depends on the answer, and settling it means probing a production endpoint that writes rows.
  • That an authenticated page response carries the CSP header. Every unauthenticated path was measured. A signed-in response needs a live Clerk session, and the middleware's NextResponse.next() path was read, not executed.

  • The other 74 worktrees. The brief mentions 89 env-shaped files across them. They are gitignored and therefore cannot reach the repository, which is the property that matters — but their contents were not enumerated.
