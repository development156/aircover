This lane assumed the product was hostile to itself. It did not ask whether the tenancy boundary works; it tried to get through it, from an ordinary member's session, against the real production database, and counted rows afterwards to see whether the refusal it was told about had actually happened.

The headline is that the boundary held everywhere it was tested. Twenty-nine tenant tables were proven with a foreign row that provably existed and was hidden. Thirty-eight hostile RPC and write probes were refused, and a sweep for the marker string every payload carried found nothing anywhere in the schema. Every webhook receiver rejected both a missing signature and a forged one.

What the audit is actually worth is in the second half of that sentence — everywhere it was tested. Sixteen tables are empty in production, so “the attacker saw nothing” is true of them whether the policy is perfect or absent. Ten of those sixteen are also outside the only isolation suite that runs in the gate. That overlap, not any single leak, is the finding this report is built around.

P1

Every table, every tenant

The table list came from the production catalog, never from an array in a file — 75 base tables, 47 carrying workspace_id, 129 policies. Each table was read three ways through PostgREST: with the anon key alone, with a token for a member of the workspace that owns the rows, and with a token for a member of a different workspace. RLS was the only thing under test; lib/supabase/server.ts refuses a service-role client, so it is also the only boundary the product has.

Ground truth — which rows exist, and how many remain after a refusal — came from a separate privileged connection opened begin read only. That separation matters more than it looks: counting rows through the same restricted token that was just refused returns zero whether the write landed or not, and every write-refusal proof would have confirmed itself.

The sweep's first run accused an innocent table, because the harness shared its blind spot

corrected

Run one reported LEAK-CROSS-TENANT on ops_credit_requests: the “attacker” read a row belonging to another workspace. The attacker was picked as the first member of any workspace other than the owner's — and that member is karunesh@sahodalabs.com, an active platform operator. The ops_select policy is using app.is_ops_admin(), so the read was the policy working exactly as designed.

Worth recording because it is the same shape as the defects this audit was looking for: a check whose selection logic cannot distinguish the case it is meant to catch from the case it is meant to permit. Operators are now excluded from the attacker pool and the operator class is reported separately, which is what makes the remaining 29 mean anything.

Radar — the highest-risk surface, and the one with no data

Production holds zero competitor subscriptions. Every Radar policy was therefore in the VACUOUS class, and the socially explosive case — a business discovering who else is watching a rival — was unobservable. Two throwaway workspaces, one shared competitor with two subscribers from different tenants, and one competitor watched by only one of them made it observable. They carried no ledger entries by design, and were removed by the same script; the schema was verified empty afterwards.

Views

Production holds one view, knowledge_current_chunks, and it is security_invoker = true. A view without it reads as its owner, so RLS on the underlying table is never consulted and workspace B would get every row of workspace A's passages. Read from pg_class.reloptions, and now armed as a catalog-driven test — with a companion case that hands the same detector a deliberately leaky view and requires it to name it, because in this tree the check would otherwise be a pass over zero views.

The prompt-injection quarantine fence could be closed from inside a page

fixed

quarantinePage ran page.markdown through neutralize and interpolated page.title raw inside JSON.stringify. JSON.stringify escapes " and \; it does not escape < or >, and the delimiters are made of exactly those.

It was reachable. extractTitle takes 300 characters from the page's own <title> and then decodes &lt; and &gt; — so a page serving &gt;&gt;&gt; never contains the literal token, and the forgery exists only after decoding. Nothing inspecting the served HTML would see a delimiter at all.

Claimed — quarantine.ts
“Fenced with a token a page cannot forge in markdown text we control.”
Measured — executed
forged CLOSE in title → 2 closes (want 1)
forged OPEN in title → 2 opens
two-page corpus → 3 closes (want 2)

Everything after the header line then renders outside the fence, in the position the system's own framing occupies. The existing suite could not see it: its page helper hardcodes title: 'About', so the fence-balance assertion only ever exercised markdown.

Title and url now go through neutralize, and Human joins the turn-marker alternation beside assistant — half the classic pair was walking through. Five tests pin it; 72/72 green in packages/research.

Three weaknesses in the same defence were measured and are not fixed here, because each is a judgement call rather than a bug. The turn-marker regex is anchored to line start and covers four English words, so mid-line turns and every ChatML, Llama, Gemma and Mistral marker pass through — and the mesh routes through OpenRouter, so the marker that matters varies by route. Nothing on the prompt path strips bidi or Unicode-tag characters, though packages/sites/src/render/escape.ts already contains a correct stripper. And the 6,000-character page budget is UTF-16 code units sized against Latin text at 2.27 chars/token, so Devanagari or Odia copy — which this product explicitly serves — admits roughly 2.3× the budgeted tokens per page.

The architectural defence is the one that holds, and the file says so: the extraction task has no tools, and its output shape pins confirmed to z.literal(false). The worst a hostile page achieves is a wrong string in a field a human has not yet approved. The fence is the second line — which is exactly why a break in it is worth fixing and not worth panicking about.

P4

What it says when things fail

This codebase is unusually good at this. Eighteen read modules distinguish “we could not check” from “there is nothing here” as separate states rather than collapsing both to empty. cheapCheck has three outcomes and its header explains why two would be a silent false negative wearing a perfect hit rate. The publish runner classifies every failure transient or permanent and carries reconnectRequired for a disconnected account.

The exception was on the most consequential path.

A customer with a workspace, watching a post fail to go out, was told to create one — under a client-error status that every 5xx alert filter skips.

Three sibling reads in that same handler have the same shape and are not fixed here: getWorkspaceRole returns null on a query error, so a failed workspace_members read answers 403 naming the caller's role; getPost returns null on error, so a database failure answers 404 plus an authorization claim; listVariants returns [], so a failed read answers 400 telling the user to write copy that already exists. Fixing those means changing three read helpers' contracts and every caller — a larger change than this lane should make unilaterally, and an owner's call.

Two more, measured and left for the owner:

  • oauth/zernio/return collapses an entitlements unknown to headroom = 0 and answers 303 zernio=limit. A dependency outage is reported to the customer as a plan decision, under a success status. The sibling start route returns 503 for the same condition.
  • delete_asset answers 500 with the user-facing sentence “That file is not in your library.” A bad id is a client error; returning it as 5xx puts ordinary user mistakes into the outage channel.

Three workspaces appeared and vanished mid-run: someone was running the e2e suite against production while this audit was in progress. Each arrived with a signup_grant of 100 and each was torn down by its own suite, cascade-deleting its ledger rows with it.

That cascade is worth naming on its own. credit_ledger carries app.block_mutations(), which refuses direct UPDATE and DELETE — but permits cascaded deletes by design, so a workspace can be offboarded. credit_ledger.workspace_id is ON DELETE CASCADE. The ledger is therefore append-only within a workspace's life and not across its deletion: delete the workspace and its entire money history goes with it, leaving no record that credits were ever granted. Deliberate, and the right call for GDPR-style erasure — but it means the ledger cannot answer “what did we issue last quarter” once a tenant leaves.

Free credits can be minted without limit, and the rule written to stop it is mounted nowhere

open

public.bootstrap_workspace is SECURITY DEFINER and granted to authenticated. Read from the server, its guards are AUTH_REQUIRED, INVALID_NAME, INVALID_SLUG, SLUG_TAKEN and FREE_PLAN_MISSING. There is no per-user workspace count. It then grants 100 credits with an idempotency key of 'grant:signup:' || v_ws.id — keyed on the workspace, so a new workspace is a new key and a fresh 100 credits.

It compounds with a second uncapped path: resolveFree runs a model task with creditsCharged: 0 and no withCredits wrapper, and isFirstResolve returns true whenever no active brand_memory row exists — so a user who never approves gets unlimited free resolves. A replayed reversal billed the customer for money already taken back

fixed

applyReversal is documented as safe to retry with a different amount under the same idempotency key, and of the ledger that is true — the RPC returns the original row with replayed: true. The outcome did not follow: reversedCredits was recomputed from a balance the first reversal had already moved, while entryId pointed at the entry that actually exists. Measured on a 1500/1000 dispute: 500 reported against 1000 recorded. Since shortfallCredits is what a credit note bills as a receivable, that bills the customer 500 credits that had already been reversed.

The true amount was on the wire the whole time — apply_ledger_entry returns to_jsonb(v_existing), the whole row — and the port was discarding it. LedgerApplyResult.entry now carries amount; making it required found all nine fakes at compile time, and each now reports the amount it was asked for rather than a placeholder.

The clamp itself is correct and was verified: an over-large chargeback clamps to what is available and reports the rest as a shortfall, retrying up to four times on a balance-floor violation rather than aborting. The constraint match is ['balance_held_le_total', 'balance_total_nonneg'] — the third constraint, balance_held_nonneg, is absent, which is worth knowing because the violation the raw path produces is balance_held_le_total and not the one you would predict.

■

The honest verdict

I would put fifty businesses on the tenancy boundary. It was attacked from an ordinary member's session against real production data and it did not move — not on reads, not on inserts, updates or deletes, not through ten confused-deputy RPC calls, not through embedded aggregates, and not through the one shared-registry design where a leak would have been socially explosive. Every refusal was confirmed by counting rows from a privileged connection afterwards rather than by believing the response.

What I would not want fifty businesses to hit is the money surface, in two specific places. Any signed-in user can mint unlimited workspaces, each carrying a fresh 100-credit grant, while the abuse rule written for exactly that sits fully implemented and never called. The same user gets unlimited uncharged model calls until they approve a brand. Neither is a security hole — nobody else's data is at risk — and both are the kind of thing that is found by an invoice rather than by an alert.

The thing I would fix before the next lane starts is not on either list. Ten tenant tables in production are outside the gate's isolation suite and are simultaneously empty, so neither the offline guard nor a live probe has ever exercised them. Their policies read correctly. That is not the same as knowing. The lanes that own those tables — knowledge, playbooks, remix, webhooks, assets — should each prove isolation the way Radar was proven here: with fixtures, a count, and the fixtures removed afterwards.

Two habits in this codebase are worth naming because they made the audit harder in the right way. The honest-gap vocabulary — unreadable, could_not_check, unmeasured as first-class states — is adopted across eighteen read modules, and the one place it was missing is the one defect this section of the audit found. And the comments state what a guard is for, which is what let five of them be mutated at exactly the right line. The defects found here were, almost without exception, in the gap between a comment's claim and the code's behaviour — which only exists because the claims were written down at all.

What this audit did not cover

  • Eleven migrations are applied in production with no file in this tree, so Radar, playbooks, the knowledge library, remix and the Zernio webhook receiver were audited from the catalog and from their own branches, not from the branch under test.
  • The deployed app at app.sahodalabs.com answers 404 for /api/cron/loop, /api/cron/metrics and /design-system — it is an older build than this branch. Public-endpoint results are true of what is deployed.
  • The Playwright leg was never run; nothing in these fixes touches UI.
  • The e2e suite was actively creating and tearing down workspaces in production throughout, so every row count here is a reading of a moving system, taken at the timestamp given.
  • No publish was executed, and no irreversible SQL was run.
